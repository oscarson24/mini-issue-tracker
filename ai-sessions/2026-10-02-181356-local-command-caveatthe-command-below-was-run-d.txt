● I wrote the plan to PLAN.md with both of your changes.

  On why there was no services folder: the first draft had a single
  src/api/issues.ts file doing the same job, but it had no shared HTTP client
  and nothing kept components from calling fetch themselves. That's now a proper
  layer:

  Services layer (frontend/src/services/)
  - apiClient.ts is one shared wrapper around fetch. It sets the /api base URL
    and JSON headers, and turns failed responses (including .NET validation
    errors) into a single error type, ApiError.
  - issueService.ts holds every API method: getAll(status?), getById(id),
    create(data) and resolve(id). If an endpoint changes, this is the only file
    to edit.
  - Calls go in one direction: components → useIssues hook → issueService →
    apiClient. Components never call fetch directly, and I added that rule to
    the acceptance criteria.
  - Tests mock fetch for the services and mock the service for components.

  Tailwind CSS
  - Tailwind v4 through the @tailwindcss/vite plugin. Setup is one plugin line
    in vite.config.ts and @import "tailwindcss"; in index.css, with no separate
    config file.
  - Setup is its own task (3.2). The form, list, filter and status badges (green
    "Open", gray "Resolved") are all styled with Tailwind, and the form and
    list stack on mobile.

  Everything else stays as you approved: Docker Compose with a separate dev file
  for hot reload, .NET 10 with controllers, Swagger at /swagger, Entity
  Framework migrations applied at startup, PATCH /api/issues/{id}/resolve, and
  filtering done on the server.

  I also added a note about hot reload on Windows: watching files through Docker
  folder mounts can be unreliable, so the dev setup turns on polling.

  You're on master but the main branch is main. Which one should the PR target?
  Once you confirm, I can start Phase 0.
